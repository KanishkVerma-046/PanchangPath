## Project

**PanchangPath** — a modern Hindu almanac website (panchangpath.com). Positioned as a cleaner, faster alternative to drikpanchang.com. Drik (astronomical) calculations, Lahiri Ayanamsha.

**Do not write "ad-free", "zero ads", "no advertising", or equivalent claims into any site copy, metadata, or generated content** (English or Hindi). The site is applying to Google AdSense, so any promise that advertising is absent will become false. Use neutral positioning instead — clean, fast, uncluttered, free to use. The `/privacy` page is the one exception: its body deliberately describes current advertising status in time-scoped, conditional language ("does not *currently* run any advertising", "If Advertising Is Added in the Future") and should stay that way.

Stack: **Astro v7** (`output: 'static'`), **Tailwind CSS v4** (`@theme` CSS custom properties), TypeScript. Deployed to **Cloudflare Pages**.

### Ayanamsha
Lahiri, computed in `src/lib/astro-core.ts`'s `lahiriAyanamsha(jd)` (takes a raw Julian Day). Fixed 2026-07-21: every page that computes ayanamsha now imports this one function instead of carrying an inline copy — see Orbital mechanics below. ~~`23.85 + 1.3612*T - 0.000136*T²` hand-fit polynomial~~ — replaced 2026-08-26: the polynomial had a confirmed, growing drift against Swiss-Ephemeris-grade references (~53″ as of 2026). Now derived from astronomy-engine's `Rotation_EQJ_ECT` (IAU 2006/P03 precession+nutation), giving the **true** (nutation-included) ayanamsha — deliberately not mean: `sunLongitude()`/`moonLongitude()`/`planetLongitude()` already return true/apparent (nutation-included) longitudes, so a mean ayanamsha would introduce a frame mismatch up to nutation's ~17″ amplitude; independently confirmed against a Swiss-Ephemeris-computed published reference table to sub-arcsecond accuracy across 1975-2026. Calibration constant `23.8572521318°` is anchored to that external table, not to the old polynomial's own J2000 value. See `docs/superpowers/plans/2026-08-26-three-initiative-scoping.md` (Initiative 1) for the full derivation, the mean-vs-true resolution, and the before/after boundary-flip verification (found and fixed a real date bug: Rahu's Dec 2026 Capricorn transit was landing on Dec 6 instead of the correct Dec 5).

### Orbital mechanics
Fixed 2026-07-21 (full-site astronomy-engine migration): the old hand-rolled Keplerian-ORB scheme (heliocentric XY + Newton-Raphson Kepler solver for Mercury–Saturn, a truncated Meeus 26-term Moon series, per-file duplicated) is gone from every file in `src/`. All 33 originally-scoped files — `kundali.ts`, `KundaliWidget.astro`, all 15 `jyotish/*.astro`, all 9 `muhurta/*.astro`, `Header.astro`'s status strip, and 4 `planets/*.astro` pages — now call `astro-core.ts`'s `astronomy-engine`-backed functions (`sunLongitude`, `moonLongitude`, `planetLongitude('mercury'|'venus'|'mars'|'jupiter'|'saturn', jd)`) instead. Rahu/Ketu still use the mean-node polynomial (`rahuLongitude`/`ketuLongitude` in `astro-core.ts`) — astronomy-engine has no dedicated lunar-node function. Verified zero `ORB`/`helioXY`/`ayanamsha(T)` matches remain anywhere in `src/` post-migration.

### Festival date policy (set 2026-10-30)
- **Reference:** every festival date is DrikPanchang **New Delhi** (fetch with `?geoname-id=1261481`; pages reached via search often default to another city such as Lancaster, CA, and come out a day early), cross-checked against at least one independent source. Record both in a source comment above the entry, and note disagreements instead of silently picking one.
- **Smarta vs Vaishnava:** the entry's `date` is DrikPanchang New Delhi's **Smarta** date. Where its Vaishnava/ISKCON (or "Gauna") date differs, keep the Smarta date and append a note to `description`/`descriptionHi`: "Vaishnava (ISKCON) devotees observe it on <date>." / "वैष्णव (इस्कॉन) भक्त इसे <date> को मनाते हैं।" Check splits on DrikPanchang's Hindu calendar (`*Smarta`/`*ISKCON` markers) and Ekadashi-dates page (`Gauna`/`Vaishnava` entries). Applied so far: Janmashtami 2025, Nirjala Ekadashi 2025, Dev Uthani Ekadashi 2025 and 2026, Ram Navami 2026.
- **Check:** `npm run audit:festival-tithi` (also printed by `npm run test:audit`) compares each entry with the Tithi engine. The engine samples a fixed 6 AM and models no observance rules, so a verified rule-based date goes in `ALLOWLIST` (`scripts/audit/lib/checkFestivalTithi.mjs`) with a one-line reason. A new festival name must be added to `EXPECTED_TITHI` or `NON_TITHI`, or the tests fail.

### Devotional Library pattern
Every category follows the same shape:
1. `src/lib/devotional/<category>.ts` exports an array of `DevotionalItem` (interface in `types.ts`: `slug`, `title`, `titleHi`, `deity?`, `deityHi?`, `icon`, `lyricsHi`, `transliteration?`, `meaning?`, `meaningHi?`, `benefits?`, `benefitsHi?`, `metaTitle?`, `metaDesc?`). `meaning`/`benefits` **do** have Hindi counterparts (`meaningHi`/`benefitsHi`) — verified 2026-08-29 that every populated `meaning`/`benefits` entry across all 11 built categories has a matching Hindi one, 1:1. Only `metaTitle`/`metaDesc` (the `<title>`/meta-description overrides added by commit `e58cc47`) are genuinely English-only, by design — don't conflate the two.
2. `src/pages/devotional/<category>/index.astro` renders `<DevotionalIndexGrid category={...} items={...} />`.
3. `src/pages/devotional/<category>/[slug].astro` has `getStaticPaths()` over the array and renders `<DevotionalDetail item={...} category={...} prev={...} next={...} />` (optionally with custom `*Label` props).
4. Flip the category's `built: false → true` in `CATEGORY_META` (`src/lib/devotional/types.ts`).
5. Wire into `src/components/Header.astro`: desktop dropdown, mobile drawer, **and** the `searchItems` array — all three, every item.
6. Single-item categories (e.g. Sundarkand) skip the grid: `index.astro` does `Astro.redirect('/devotional/<category>/<slug>', 301)` straight to the one detail page.

**Sourcing long/sacred texts accurately**: for anything where word-for-word fidelity matters (full stotras, chalisas, Durga Saptashati, Sundarkand), do not reconstruct from memory if a reference source is available — `WebFetch` **cannot** return verbatim text (hard ~125-character quote limit, it summarizes/paraphrases instead). Instead: `curl` the raw HTML directly (with a browser `User-Agent`), strip tags in Node (`content.replace(/<script.../gi,'').replace(/<[^>]+>/g,'')`, decode `&nbsp;`/`&#x...;` entities), then locate the verse content between a start marker (e.g. a chapter heading string) and an end marker (drikpanchang.com pages end article content right before a `A+AA-` font-size-toggle UI string, followed by prev/next nav — cut there to drop nav/footer junk). Verify extraction by checking the source's own verse-count colophon (e.g. "एवमादितः॥104॥") or sequential numbering (Doha 1→60 with no gaps/dupes) before trusting the result. See git history for the Durga Saptashati / Sundarkand commits for a working extraction script.

## Critical Gotchas

- **Apostrophes in TypeScript strings** — must be escaped with backslash (`\'`) inside single-quoted TS strings, or use template literals
- **Google Fonts** — use `<link>` in HTML `<head>`, NOT `@import` in CSS (Tailwind v4 breaks `@import` ordering)
- **Client-side scripts in static Astro CAN import from TS server modules** — corrected 2026-07-20: this was previously (incorrectly) documented as impossible. Astro's `<script>` tags (without `is:inline` or other attributes) are processed by Vite, support TypeScript, and bundle local file imports automatically — verified empirically and via Astro's own docs. Every calculator on the site now imports its astronomy math from `src/lib/astro-core.ts`/`src/lib/panchang.ts`/`src/lib/kundali.ts` (fixed 2026-07-21, full-site consolidation — see `docs/superpowers/plans/2026-07-21-full-site-astronomy-engine-scope.md` for the original inventory this closed out). **One exception**: `<script define:vars={{...}}>` implicitly forces `is:inline`, which blocks Vite from resolving `import` statements entirely (documented Astro behavior, not a bug) — every page that used `define:vars` to inject server data (icon SVGs, etc.) had to be converted to a plain `<script>` that imports that same data directly from its source module instead, before it could import astro-core functions too.
- **Never run `git stash` or other whole-tree git ops inside a worktree shared with concurrent background agents** — `git stash` internally does a `git reset --hard`, which silently wipes every other in-flight agent's uncommitted edits in that worktree, not just your own. Hit this during a 6-agent parallel dispatch on 2026-07-21; recovered via a protective WIP commit, but avoiding it is much cheaper than recovering from it. Prefer per-file `git checkout <ref> -- <path>` if you need to isolate a diff.
- **`gh pr merge -d/--delete-branch` fails from inside a git worktree if the PR's base branch (e.g. `master`) is checked out in a different worktree** — errors `fatal: 'master' is already used by worktree`. Merge without `-d` first (it succeeds), then delete the remote branch separately with `git push origin --delete <branch>`.
- **`npm run deploy`'s predeploy clean-tree guard (`scripts/check-clean-tree.mjs`, added 2026-08-16) has a bypass it prints on failure** (`npm run build && npx wrangler pages deploy dist --project-name=panchangpath --branch=main`). That bypass is **not scoped to untracked/docs files** — it skips the clean-tree check entirely and deploys whatever is on disk, tracked or not, committed or not. It's only "safe" in a given instance if you've separately verified everything else dirty at the time is something you intend to ship (e.g. pre-existing unrelated untracked docs) — the command itself enforces no such scoping.
- **`getStaticPaths()`** — required for all dynamic routes (`festivals/[slug].astro`, `events/[id].astro`, `rashifal/[rashi].astro`, `devotional/*/[slug].astro`, `panchang/[region].astro`)
- **`festivals.astro` + `festivals/[slug].astro`** coexist fine — file vs directory have different filesystem names
- **Passing data to client scripts in static Astro** — use `define:vars={{ myData }}` on `<script>` tags to pass server-computed values (e.g. `PRASHNAVALI_ANSWERS` in `prashnavali.astro`) into client-side code; a client `<script>` block cannot read `Astro.props` or other frontmatter variables directly — but it CAN `import` functions/data from a `.ts` module in `src/lib/` (see the corrected gotcha above), which is a different thing from reading frontmatter
- **`WebFetch` cannot return verbatim text** — hard ~125-char quote limit, always summarizes. Use `curl` + manual HTML-tag-stripping for anything requiring exact text (see "Sourcing long/sacred texts accurately" above).
- **`astro check` reports ~900+ TypeScript errors** — nearly all are the same pattern (`document.getElementById(...)` returning untyped `HTMLElement`, missing null-checks) across every calculator's inline `<script>` block. This is pre-existing, doesn't block `astro build`, and isn't worth mass-fixing; don't be alarmed by the count.
- **No browser-automation CLI in this harness** — Playwright is installed as a project devDependency though. To screenshot/verify UI: write a `.cjs` script (package.json has `"type":"module"`, so plain `.js` files are ES modules — `.cjs` lets you `require('playwright')`), and run it from the project root so `node_modules` resolves (running from an external scratchpad dir fails with `MODULE_NOT_FOUND`).
- **Cloudflare Pages propagation lag** — after `npm run deploy`, the printed deployment-specific hash URL (`https://<hash>.panchangpath.pages.dev`) is live immediately; the `panchangpath.pages.dev` production alias can take 1-2 min to catch up. Verify against the hash URL first, or `npx wrangler pages deployment list --project-name=panchangpath` to confirm which commit is current Production.
- **`npm run deploy`'s exit code is not reliable evidence a deploy succeeded** — hit this 2026-08-21: the Wrangler upload step failed mid-way ("Failed to upload files... Error: {}"), but the overall command still exited 0. Always confirm with `npx wrangler pages deployment list --project-name=panchangpath` (check the top row's Source commit and timestamp) after any deploy before reporting it as done — don't trust the printed "Deployment complete!" or exit code alone. If the upload did fail, just retry `npx wrangler pages deploy dist --project-name=panchangpath --branch=main` (the `dist/` from the prior build is still valid, no need to rebuild).
- **Live-verifying rendered HTML requires `curl -sL`** — directory-style routes (`/blog`, and any other path whose page lives at `pages/<name>/index.astro`) issue a **308 to the trailing-slash form with a zero-byte body**. An un-redirected fetch returns an empty string, not the page, so a grep over it finds neither the expected string nor the bad one — which reads as "the fix is missing" when the page is actually fine. This produced a false regression report on 2026-08-13 (an audit claimed `/blog`'s footer still said "completely ad-free"; live was correct, the audit was matching the pre-`535a731` string from stale input). Reliable sitewide sweep: pull `https://panchangpath.com/sitemap.xml` (399 URLs), extract `<loc>`, crawl all with `curl -sL`, then grep. Two of those are meta-refresh redirect stubs (`devotional/sundarkand`, `kundali`) which carry no footer — curl does not follow meta refresh, so **397/399 is the correct "all real pages" denominator**, not a coverage gap. Scan bilingually: an English-only grep misses Hindi copy carried in `data-hi` attributes.
- **Devanagari conjuncts can render garbled in chat/terminal fonts** — when proposing new Hindi text for approval, don't just paste it in the response; stage it live (uncommitted) on the real page and screenshot it via Playwright so it renders in the site's actual font.
- **IndexNow submission is automatic — do not manually call it after a normal publish+deploy.** Fixed 2026-09-11: Bing Webmaster Tools flagged the site's prior setup ("submit the whole sitemap daily, document a manual single-URL call nobody actually ran") as "IndexNow is in batch mode." `npm run deploy`'s `postdeploy` lifecycle step (`scripts/indexnow-deploy-diff.mjs`) now runs automatically after every deploy: it finds the commit that was live before this deploy via `wrangler pages deployment list --json` (Cloudflare Pages already tracks deploy history by commit, so no separate state file is needed), diffs it against the current `HEAD` commit, maps the changed files to live URLs (`scripts/lib/indexnow-diff.mjs` — static page files map directly; the content-data files behind `getStaticPaths()` routes, e.g. `src/lib/festivals.ts`, `src/lib/blog.ts`, `src/lib/devotional/*.ts`, are diffed item-by-item by slug so only the actually-changed entries' URLs are submitted, not the whole section), and submits only those via `submitToIndexNow()`. When a registered data file changes, the static pages that list its data are submitted too (2026-10-30: `pagesDependingOn()` derives them from the import graph, e.g. `/`, `/festivals/`, `/festivals/archive/`, `/calendar/` for `festivals.ts`; it does not follow layout chrome such as the Header, which would mean every page). It fails open everywhere (no prior deployment to diff against, IndexNow being down, a shallow-clone gap) — it logs and skips rather than ever blocking or failing a deploy. **A future session publishing new content does not need to call `indexnow-submit.mjs` manually — that would double-submit** on top of what `postdeploy` already sends; manual single-URL submission is still the right tool only for a genuinely out-of-band case (a URL that changed without going through a normal `npm run deploy`). The old daily full-sitemap submission is gone from `.github/workflows/daily-rebuild.yml`; a much-reduced weekly (not daily) full-sitemap fallback remains at `.github/workflows/weekly-indexnow-safety-net.yml`, explicitly a rare catch-all (e.g. for a shared-component edit that ripples into many pages without touching a page file or a registered content-data file directly) and not the primary channel. See `docs/superpowers/plans/2026-09-11-indexnow-diff-based-submission.md` for the full design. Key verification file: `public/40561200baba459aa3fc4b890c7e49df.txt`; the key itself (`40561200baba459aa3fc4b890c7e49df`) is public by design (published in that file and sent in every API call), not a secret.
