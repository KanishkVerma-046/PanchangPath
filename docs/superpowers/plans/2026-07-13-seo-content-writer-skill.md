# SEO Content Writer Skill + /blog Section — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a `/blog` section for PanchangPath (data model, list/detail pages, nav wiring) and a project Claude Code skill (`.claude/skills/seo-content-writer/`) that researches and drafts SEO blog posts for it through a research → outline-approval → draft workflow.

**Architecture:** The `/blog` section follows this repo's established Devotional Library pattern exactly — a typed data array (`src/lib/blog.ts`), a shared index-grid component, a shared detail component, and two Astro pages (`/blog` index, `/blog/[slug]` detail via `getStaticPaths()`). The skill is a Markdown `SKILL.md` plus four reference files under `.claude/skills/seo-content-writer/references/`; one of those references (`internal-links.md`) is generated by a standalone Node script rather than hand-maintained, so it can be re-run whenever pages are added.

**Tech Stack:** Astro v7 (`output: 'static'`), Tailwind CSS v4, TypeScript, plain Node.js (`node:fs`/`node:path`, no new dependencies).

## Global Constraints

- No mention anywhere in generated content or reference docs that PanchangPath is ad-free.
- Never name drikpanchang.com or any other competitor in generated content or reference docs.
- English only for v1 — no Hindi/bilingual blog content.
- No client-wins/testimonials/social-proof step in the skill workflow.
- No manually-uploaded sitemap CSV — `internal-links.md` is generated from the codebase by `scripts/generate-link-map.mjs`.
- No packaging as a distributable `.zip` — this is a live, in-repo project skill.
- Apostrophes inside single-quoted TypeScript strings must be escaped with `\'`, or use a template literal instead.
- Individual blog posts do not get their own header nav entries — only the `/blog` hub does, matching how `/devotional` and `/festivals` work today.
- `npm run build` is the correctness gate for all Astro changes in this repo (not `astro check`, which reports a large pre-existing noise count unrelated to this work).

```ts
export interface BlogPost {
  slug: string;
  title: string;
  description: string;
  publishDate: string; // ISO date, e.g. '2026-07-13'
  keywords: string[];
  contentHtml: string;
}

export const BLOG_POSTS: BlogPost[] = [];

export function estimateReadingTime(contentHtml: string): number {
  const text = contentHtml.replace(/<[^>]+>/g, ' ');
  const words = text.trim().split(/\s+/).filter(Boolean).length;
  return Math.max(1, Math.round(words / 200));
}

export function sortedByNewest(posts: BlogPost[]): BlogPost[] {
  return posts.slice().sort((a, b) => b.publishDate.localeCompare(a.publishDate));
}
```

- [ ] **Step 1: Write `scripts/generate-link-map.mjs`**

```js
#!/usr/bin/env node
// Scans src/pages/**/*.astro for <Layout title="..." description="..."> props
// and writes a Markdown internal-link table for the seo-content-writer skill.
// Re-run this after adding or removing pages: node scripts/generate-link-map.mjs

import { readdirSync, readFileSync, writeFileSync, mkdirSync } from 'node:fs';
import { join, relative, dirname, sep } from 'node:path';

const ROOT = process.cwd();
const PAGES_DIR = join(ROOT, 'src', 'pages');
const OUTPUT_FILE = join(ROOT, '.claude', 'skills', 'seo-content-writer', 'references', 'internal-links.md');

function walk(dir) {
  let files = [];
  for (const entry of readdirSync(dir, { withFileTypes: true })) {
    const full = join(dir, entry.name);
    if (entry.isDirectory()) {
      files = files.concat(walk(full));
    } else if (entry.isFile() && entry.name.endsWith('.astro')) {
      files.push(full);
    }
  }
  return files;
}

function fileToUrl(filePath) {
  let rel = relative(PAGES_DIR, filePath).split(sep).join('/');
  rel = rel.replace(/\.astro$/, '');
  if (rel === 'index') return '/';
  if (rel.endsWith('/index')) rel = rel.slice(0, -'/index'.length);
  return '/' + rel;
}

function decodeAndEscape(str) {
  return str
    .replace(/&amp;/g, '&')
    .replace(/&quot;/g, '"')
    .replace(/&#39;/g, "'")
    .replace(/\|/g, '\\|');
}

const links = [];
for (const file of walk(PAGES_DIR)) {
  const rel = relative(PAGES_DIR, file).split(sep).join('/');
  if (rel.includes('[')) continue; // dynamic routes have no single canonical URL to link to
  if (rel === '404.astro') continue; // not a real content link target

  const src = readFileSync(file, 'utf-8');
  const layoutMatch = src.match(/<Layout\b([\s\S]*?)>/);
  if (!layoutMatch) continue;
  const propsBlock = layoutMatch[1];

  const titleMatch = propsBlock.match(/\btitle="([^"]*)"/);
  if (!titleMatch) continue; // title is a JS expression, not a static string — skip

  const descMatch = propsBlock.match(/\bdescription="([^"]*)"/);

  links.push({
    url: fileToUrl(file),
    title: decodeAndEscape(titleMatch[1]),
    description: descMatch ? decodeAndEscape(descMatch[1]) : '',
  });
}

links.sort((a, b) => a.url.localeCompare(b.url));

const header = [
  '# Internal Link Map',
  '',
  'Auto-generated by `scripts/generate-link-map.mjs` — do not hand-edit.',
  'Re-run the script after adding or removing pages: `node scripts/generate-link-map.mjs`',
  '',
  '| URL | Title | Description |',
  '|---|---|---|',
].join('\n');

const rows = links.map(l => `| ${l.url} | ${l.title} | ${l.description} |`).join('\n');

mkdirSync(dirname(OUTPUT_FILE), { recursive: true });
writeFileSync(OUTPUT_FILE, header + '\n' + rows + '\n');

console.log(`Wrote ${links.length} internal links to ${relative(ROOT, OUTPUT_FILE)}`);
```

## Audience

Two overlapping readers:
- **Traditional practitioners** in India who already know the vocabulary (Tithi, Nakshatra, Muhurta) and want accurate timing fast.
- **Hindu diaspora abroad** who may need more context (what a term means, why a date matters) without being talked down to.

Write so both groups feel served: define terms briefly on first use, but never over-explain to the point of condescension.

## Voice principles

1. **Precise, not preachy.** State facts about tithis, festivals, and muhurtas plainly. Avoid devotional exhortation ("you must," "it is essential that every Hindu...").
2. **Accessible, not dumbed-down.** Assume an intelligent reader encountering a term for the first time — explain, don't oversimplify.
3. **Confident, not mystical.** Prefer concrete language ("Ekadashi falls on the 11th tithi of each paksha") over vague spiritual abstraction ("Ekadashi carries a special cosmic energy").
4. **Warm, not salesy.** No countdown urgency ("Don't miss out!"), no fake scarcity, no exclamation-point enthusiasm.

## Do

- "Griha Pravesh muhurtas are chosen based on the Tithi, Nakshatra, and day of the week — Dwadashi, Panchami, and Dashami are generally considered favorable."
- "Ekadashi is the eleventh tithi of each lunar fortnight, observed with a fast dedicated to Vishnu."
- "Check your city's sunrise time before relying on a Choghadiya table — the slots shift with local sunrise."
- "The Hanuman Chalisa, composed by Tulsidas, is recited for protection and courage."

## Avoid

- Positioning claims about the site's business model or advertising — those live in `SKILL.md`'s baked-in variables, not blog copy.
- Naming or comparing against any competing panchang/astrology site — see `SKILL.md`'s baked-in variables for the specific name to never use.
- Medical or legal-advice-style astrology claims ("this gemstone will cure your illness," "this muhurta guarantees a positive court verdict").
- Empty buzzwords: "game-changer," "revolutionary," "unlock your destiny," "ancient secret."
- Manufactured urgency: "Only X days left," "Don't miss this rare alignment."
- Second-person commands about belief ("You must perform this puja" → prefer "This puja is traditionally performed...").

## Structural conventions

- Primary keyword in the title, first paragraph, and 2-3 H2s — worked in naturally, never stuffed.
- FAQ-style H2/H3 sections should be self-contained: a reader landing mid-page via a search snippet should get a full answer without needing the rest of the article.
- Internal links use descriptive anchor text tied to the destination page's actual content (e.g., "check today's Choghadiya timings" linking to `/muhurta/choghadiya`), never "click here."
- All external sources are paraphrased and linked with descriptive anchor text — never quoted verbatim, never a naked URL.

# SEO Content Writer — PanchangPath

Writes SEO blog posts for panchangpath.com through a research-then-approval-then-draft workflow. Every post goes through an explicit outline-approval checkpoint before full drafting begins — never skip straight to a full draft.

## Baked-in variables

| Variable | Value |
|---|---|
| Brand | PanchangPath |
| URL | https://panchangpath.com |
| Default word count | 1500 |
| Language | English only |
| Audience | People seeking accurate Hindu Panchang/festival/muhurta timings — traditional practitioners and Hindu diaspora abroad |
| Primary topics | Panchang & Tithi, Festivals & Vrats, Muhurta timing, Jyotish/Kundali, Rashifal, Devotional practice |
| Competitor mentions | Never name drikpanchang.com or any other competitor, anywhere |
| Negative keywords (baseline) | "guaranteed," "overnight," medical/legal-advice-style astrology claims — extend per-post in Step 1 |

Never mention that PanchangPath is ad-free in generated content.

## Workflow

### Step 1 — Gather requirements

Ask the user for (skip questions they've already answered in their request):
- Primary keyword
- Topic/angle
- Target audience slice (default: general PanchangPath audience)
- Word count (default: 1500)
- Negative keywords/phrases to avoid for this post (in addition to the baseline above)
- Optional CTA or related-topic notes

If the user hasn't specified a topic at all, suggest 2-3 options from `references/keyword-targets.md`.

### Step 2 — Research

1. Run 3-7 web searches covering search intent, statistics, trends, and expert perspectives on the topic.
2. Read `references/internal-links.md` and identify 3-5 relevant internal pages to link to. If it looks stale (missing a page you know exists, e.g. a recently-added calculator), re-run `node scripts/generate-link-map.mjs` from the repo root before continuing.
3. Compile all sources with specific placement recommendations: which section they support, and what anchor text to use.

### Step 3 — Present outline & recommendations [APPROVAL REQUIRED]

Present, in this order:
1. Search-intent analysis (what is the reader actually trying to find out?)
2. Complete H2/H3 outline
3. Source integration plan — 5-10 sources with URLs and where each will be used
4. Internal-linking plan — 3-5 links with reasoning for each

Explicitly ask: "Does this outline look right? I won't start drafting until you approve it." **Do not draft the post before this is approved.** If the user requests changes, revise and re-present before proceeding.

### Step 4 — Write the full post

Only after Step 3 is approved. Follow:
- The approved outline exactly.
- `references/tone-of-voice.md` for voice and the do/avoid lists.
- `references/seo-checklist.md` as the acceptance bar.

Structure:
- **Intro** (150-200 words): hook, problem, promise.
- **Body** (4-6 H2s, 2-4 H3s each, ~1200-1400 words combined for the 1500-word default): primary keyword worked naturally into 2-3 H2s.
- **2-4 FAQ-style H2/H3 sections**: self-contained Q&A, each answerable on its own without the rest of the article.
- **Conclusion** (100-150 words): summary + CTA.

Sources: paraphrase everything, embed as contextual hyperlinks with descriptive anchor text (never "click here," never a naked URL, never a verbatim quote).

Internal links: 3-5, woven naturally, using the pages and reasoning from the approved Step 3 plan.

Write the body as HTML (matching the `contentHtml` field's rendering — `<h2>`, `<h3>`, `<p>`, `<ul>`/`<ol>`, `<a href="...">` tags; no `<html>`/`<body>` wrapper).

Before presenting the draft as done, run it against every item in `references/seo-checklist.md`.

### Step 5 — Publish

1. Open `src/lib/blog.ts` and append a new entry to the `BLOG_POSTS` array:
   ```ts
   {
     slug: 'my-post-slug',       // kebab-case, derived from the title
     title: 'Post Title',
     description: 'Meta description, 150-160 characters.',
     publishDate: '2026-07-13',  // today's date, ISO format
     keywords: ['primary keyword', 'secondary keyword'],
     contentHtml: `<p>...</p>`,  // the full HTML body from Step 4
   }
   ```
2. Run `npm run build` and confirm it succeeds with the new post included.
3. Confirm the post is reachable at `/blog/<slug>` (the `/blog` hub link is already wired into Header.astro's nav — no per-post nav changes needed; only the hub link exists in nav, matching how `/devotional` and `/festivals` work).
